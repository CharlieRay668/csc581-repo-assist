Problem: Evaluate whether idempotency storage should be per-route/per-user/global; propose a schema and expiration policy.

Response: ### Idempotency Storage Evaluation and Proposal Idempotency is crucial in preventing duplicate submissions, especially for sensitive operations like creating a referral in a referral management application. The scope of idempotency storage (per-route, per-user, global) depends on the specific operations and their business logic. #### 1. Idempotency Scope **Conclusion:** Idempotency should be **per-user and per-operation**. **Rationale:** * **Prevents Cross-User Duplication:** Ensuring that the same user cannot create multiple identical referrals (e.g., for the same referrer and referred email) prevents confusion and ensures data integrity. * **Per-Operation Granularity:** Different operations (e.g., `createReferral`, `redeemReferral`) should be treated as separate idempotent operations, even if they belong to the same user. This prevents, for example, a user from accidentally creating a new referral that *also* redeems an old one if the same key is used. * **Global Uniqueness:** While the key should be globally unique, its components should ensure it's specific to the user and the operation. This doesn't prevent multiple users from performing the same action, which is generally acceptable. #### 2. Proposed Idempotency Key Schema The idempotency key should uniquely identify a user's attempt to perform a specific operation (e.g., creating a referral, redeeming a referral). **Schema:** ```typescript // src/utils/idempotency.ts export interface IdempotencyKey { // A unique identifier for the user. This should be a secure, random UUID // generated when the user authenticates. It ensures that operations are // scoped to a single user. userId: string; // A unique identifier for the specific resource being created. This ensures // that if a user tries to create a referral for the same referrer and referred // email, it's considered an idempotent operation. referralId: string; } ``` **Key Generation Example (for `createReferral`):** ```typescript // src/utils/idempotency.ts export function generateCreateReferralKey(userId: string, referrerId: string, referredEmail: string): string { return `${userId}:${referrerId}:${referredEmail}`; } ``` **Key Generation Example (for `redeemReferral`):** ```typescript // src/utils/idempotency.ts export function generateRedeemReferralKey(userId: string, referralId: string): string { return `${userId}:${referralId}`; } ``` **Explanation:** * **`userId`**: Ensures operations are user-specific. * **`referralId`** (for `createReferral`): Ensures a user cannot create multiple identical referrals for the same combination of referrer and referred email. * **`referralId`** (for `redeemReferral`): Ensures a user cannot attempt to redeem the same referral multiple times. #### 3. Idempotency Storage **Proposed Implementation:** A Redis cache. **Reasons:** * **High Performance:** Redis provides fast-read/write operations, making it suitable for preventing duplicate submissions. * **Expiration:** Redis supports time-to-live (TTL) for keys, allowing for automatic cleanup of old idempotency tokens. * **Scalability:** Redis clusters can easily scale to handle increased load. **Storage Operations Example (`src/utils/idempotency.ts`):** ```typescript import redis from 'redis'; import { promisify } from 'util'; const client = redis.createClient({ url: process.env.REDIS_URL, }); const setAsync = promisify(client.SET).bind(client); const getAsync = promisify(client.GET).bind(client); const delAsync = promisify(client.DEL).bind(client); export async function storeIdempotentOperation(key: string): Promise<void> { // Store a flag to indicate that the operation has been seen await setAsync(key, "processed", 'EX', IDEMPOTENCY_EXPIRATION_MS); } export async function isIdempotentOperation(key: string): Promise<boolean> { const value = await getAsync(key); return value === "processed"; } export async function forgetIdempotentOperation(key: string): Promise<void> { await delAsync(key); } ``` #### 4. Expiration Policy **Proposed Expiration:** 24 hours (86400 milliseconds). **Reasons:** * **Prevents Stale Tokens:** After a day, the likelihood of a user re-submitting an old form is low. This balances between preventing duplicate submissions and not holding onto unnecessary data indefinitely. * **Automated Cleanup:** Redis will automatically evict old keys once their TTL expires, reducing storage overhead. **Environment Variable:** ```typescript // src/utils/idempotency.ts const IDEMPOTENCY_EXPIRATION_MS = 86400; // 24 hours ``` #### 5. Implementation in Routes The idempotency check and storage should occur at the beginning of the request handler, before any database operations. **Example Implementation (`src/app/api/referrals/route.ts`):** ```typescript import { NextRequest, NextResponse } from 'next/server'; import { RedisClientType } from 'redis'; import { generateCreateReferralKey, storeIdempotentOperation, isIdempotentOperation, forgetIdempotentOperation } from '@/utils/idempotency'; import { auth } from '@/utils/auth'; import prisma from '@/utils/db'; export async function POST(req: NextRequest) { try { // Authentication: Ensure the request is from an authenticated user. const user = await auth(); if (!user) { return NextResponse.json({ error: "Unauthorized" }, { status: 401 }); } // Parse the request body to extract referrer ID and referred email. const body = await req.json(); const { referrerId, referredEmail } = body; // Generate the idempotency key for creating a referral. const idempotencyKey = generateCreateReferralKey(user.id, referrerId, referredEmail); // Check if this operation has been seen before. if (await isIdempotentOperation(idempotencyKey)) { // If seen, return a 200 OK with a message indicating idempotency. return NextResponse.json({ message: "Referral creation request already processed." }, { status: 200 }); } // If not seen, process the operation. // ... (existing logic to create the referral in the database) ... // After successful processing, store the operation as seen. await storeIdempotentOperation(idempotencyKey); return NextResponse.json(newReferral, { status: 201 }); } catch (error) { console.error("Error processing referral creation:", error); return NextResponse.json({ error: "Internal Server Error" }, { status: 500 }); } } ``` **Explanation:** * **Authentication (`src/utils/auth.ts`):** Ensures that only authenticated users can create referrals. * **Idempotency Check:** Before any database write, the system checks Redis to see if this exact combination of user, referrer, and referred email has been processed. * **Storage:** If it's a new operation, it's processed, and the key is stored in Redis with an expiration of 24 hours. * **Forget:** If the user successfully completes the operation (e.g., by updating their profile), the key can be explicitly forgotten to free up Redis memory (optional but recommended for completed operations that are no longer relevant). --- This approach ensures that referral creation requests are idempotent per user and per referred combination, preventing duplicate entries, while effectively managing storage with Redis' TTL mechanism.
