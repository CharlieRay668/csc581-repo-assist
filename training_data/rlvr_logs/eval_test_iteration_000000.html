Problem: Evaluate whether idempotency storage should be per-route/per-user/global; propose a schema and expiration policy.

Response: ### Idempotency Storage Evaluation Idempotency is crucial for preventing duplicate submissions, especially in forms that trigger server-side mutations (e.g., creating a referral). The scope of idempotency storage (per-route, per-user, global) should be determined by the application's mutation patterns and the likelihood of duplicate requests. #### Proposed Idempotency Storage Scope: Per-User and Per-Action (Route-Specific) For the PRFC Connect application, particularly for the `/api/referrals` route (src/app/api/referrals/route.ts), idempotency tokens should be stored **per-user and per-action**. This approach balances scope and efficiency, preventing duplicate submissions for the same user performing the same action (e.g., creating a referral with the same `referralCode`). #### Proposed Idempotency Token Schema The idempotency token should uniquely identify a request and its associated user, along with the specific action (e.g., `createReferral`). ```typescript // src/utils/idempotency.ts export interface IdempotencyKey { // A unique identifier generated by the client for the specific request. client_id: string; // The authenticated user's ID. This ensures that different users can perform the same action // and have their own separate idempotency. user_id: string; // A unique, non-semantic identifier for the action being performed. This differentiates // between creating a referral, updating a referral, etc. action: string; // A timestamp indicating when the idempotency key was created. createdAt: number; } ``` #### Proposed Expiration Policy Idempotency keys should have a **short expiration time** to balance resource usage and effectiveness. Old keys that have not been used are no longer relevant, and holding onto them indefinitely consumes memory. - **Expiration Time**: 5 minutes. - **Grace Period**: 10 minutes (keys expire after 5 minutes but can be retrieved for 10 minutes to allow late submission). This means that if a user attempts to submit the same form after 5 minutes, the key will no longer exist, and the request will be processed as a new one. However, if the duplicate request arrives within 10 minutes, the key will still be present, and the duplicate can be rejected. #### How to Implement 1. **Client-Side**: When the user submits the form (e.g., `handleSubmit` in `src/app/(user)/create-referral/page.tsx`), the client should generate a unique `client_id` (UUID) and include it in the request headers. ```typescript // Example: Generating a UUID client-side (e.g., in a React component) const client_id = uuidv4(); // Ensure a cryptographically secure UUID const headers = { "Authorization": `Bearer ${token}`, "Idempotency-Key": client_id, "UserId": user.id, }; ``` 2. **Server-Side (`src/app/api/referrals/route.ts`)**: At the beginning of the POST handler, check if an `IdempotencyKey` exists for the given `client_id`, `user.id`, and action (`createReferral`). If it exists within the grace period, return the cached response. Otherwise, create a new key and store it. ```typescript // src/app/api/referrals/route.ts // Inside the POST handler if (idempotentResponse) { return new NextResponse(idempotentResponse.body, { status: idempotentResponse.status, headers: idempotentResponse.headers, }); } // Otherwise, proceed with the mutation // ... (createReferral logic) ... // After successful mutation, store the idempotency key const idempotencyKey: IdempotencyKey = { client_id: client_id, user_id: user.id, action: "createReferral", createdAt: Date.now(), }; await setIdempotencyKey(idempotencyKey); ``` 3. **Storage**: Use a fast, in-memory cache like Redis or `node-cache` to store and retrieve idempotency keys. Redis is recommended for distributed systems or if the application scales horizontally. For a single-node application, `node-cache` is lightweight and sufficient. ```bash // package.json (add to dependencies) "node-cache": "^9.0.0" ``` ```typescript // src/utils/idempotency.ts import { Cache } from 'node-cache'; const idempotencyCache = new Cache({ stdTTL: 300, useClones: false }); // 5 minutes export async function setIdempotencyKey(key: IdempotencyKey): Promise<void> { idempotencyCache.set(generateCacheKey(key), key); } export async function getIdempotencyKey(client_id: string, user_id: string, action: string): Promise<{ body: any; status: number; headers: Headers } | null> { const cacheKey = generateCacheKey({ client_id, user_id, action }); const cachedKey = idempotencyCache.get(cacheKey); if (!cachedKey) { return null; } // Check if expired (createdAt + 5 minutes > now) or grace period (createdAt + 10 minutes < now) if (Date.now() > cachedKey.createdAt + 5 * 60 * 1000 || Date.now() > cachedKey.createdAt + 10 * 60 * 1000) { idempotencyCache.del(cacheKey); return null; } // Return a mock response (in a real scenario, the body would be the newly created referral object) const body = await prisma.referral.create({ data: { referralCode, // ... other fields }, select: { id: true, referralCode: true, // ... other fields to return }, }); return { body: JSON.stringify(body), status: 201, headers: new Headers({ "Content-Type": "application/json", }), }; } function generateCacheKey(key: { client_id: string; user_id: string; action: string }): string { return `${key.client_id}-${key.user_id}-${key.action}`; } ``` #### Justification - **Per-User**: Ensures that one user's duplicate submissions don't inadvertently affect or interfere with another user's submissions. - **Per-Action**: Differentiates between creating, updating, or deleting referrals, which are semantically distinct operations. - **Short Expiration with Grace Period**: Minimizes memory footprint while still allowing for a small window to handle very late duplicate submissions that might otherwise be processed correctly if the key had already expired. This approach provides robust protection against duplicate submissions without over-restricting valid retries or consuming unnecessary resources.
