Problem: Evaluate whether idempotency storage should be per-route/per-user/global; propose a schema and expiration policy.

Response: ### Idempotency Storage Evaluation and Proposal Idempotency is a critical aspect of API design to ensure that repeated identical requests have the same effect as the first one. In the context of the PRFC Connect application, specifically the `src/app/api/referrals/route.ts` file, idempotency should be managed **per-user and per-route**. #### Justification: 1. **Per-User**: - Referrals are inherently tied to a specific user. For example, creating a new referral or redeeming a code should only be applied once per user to prevent duplicates. - `src/app/api/referrals/route.ts` handles both `POST` (create a referral) and `PATCH` (redeem a code) requests, which are user-specific actions. - Storing idempotency keys globally would not differentiate between similar requests from different users, leading to incorrect behavior (e.g., preventing a valid user from creating a referral if another user with the same key attempted it before). 2. **Per-Route**: - The `POST` and `PATCH` endpoints in `src/app/api/referrals/route.ts` perform distinct operations (creation vs. redemption). - These operations should have separate idempotency checks to ensure that, for example, a user cannot create the same referral multiple times, and also cannot attempt to redeem the same code multiple times. - Combining them under a single idempotency key would lead to unintended side effects (e.g., preventing a valid redemption after a successful creation, or vice versa). --- ### Proposed Idempotency Key Schema The idempotency key should be a unique identifier generated by the client for each request. The key should be constructed to uniquely identify the specific operation (route) and the user: ```plaintext userId_operationName_requestBodyHash ``` **Example**: If `userId = "123"`, `operationName = "createReferral"`, and the `requestBody` hash is `"abcdef1234"`, the idempotency key would be: ```plaintext "123_createReferral_abcdef1234" ``` **Fields**: - **userId**: A unique identifier for the user (e.g., extracted from authentication/authorization middleware). - **operationName**: A string that uniquely identifies the specific API operation, such as `"createReferral"` or `"redeemCode"`. - **requestBodyHash**: A cryptographic hash (e.g., SHA-256) of the relevant parts of the request body. This ensures that different requests with the same intent but minor payload changes are treated as distinct. For `createReferral`, hash the `referralCode` and `redeemedBy`. For `redeemCode`, hash the `referralCode`. **Implementation Notes**: - The client is responsible for generating this key. The server then checks against its idempotency storage. - Only store keys that are expected to change state. For `GET` requests, which retrieve data and should not change state, an idempotency key is generally not necessary. --- ### Idempotency Storage Proposal **Storage Mechanism**: Use a **Redis cache** to store idempotency keys. Redis provides fast access, supports expiration, and is easily scalable. **Redis Key Structure**: ```plaintext "idempotency:{userId}:{operationName}:{requestBodyHash}" ``` **Redis Value**: A simple boolean flag, e.g., `"true"`, indicating that the request has been processed. **File Integration**: Introduce a new file, `src/lib/idempotency.ts`, to handle the generation of idempotency keys and interactions with Redis. --- ### Expiration Policy Idempotency keys should expire after a reasonable period to free up storage and reduce the risk of key collisions due to very old requests. **Expiration Time**: - **5 minutes**. **Rationale**: - 5 minutes is sufficient for most typical referral workflows (e.g., a user might have a short window to complete a referral creation or redemption). - It balances preventing duplicate processing with storage efficiency. - If a user retries a request after 5 minutes, it's generally considered an error or a new intent, and the system can process it as a fresh request. **Implementation**: In `src/lib/idempotency.ts`, use Redis' `EXPIRE` command or set the `TTL` (Time-To-Live) when storing the key. --- ### Summary - **Idempotency Scope**: Per-user and per-route. - **Schema**: `userId_operationName_requestBodyHash`. - **Storage**: Redis hash (e.g., `idempotency:{userId}:{operationName}:{requestBodyHash}`). - **Expiration**: 5 minutes. This approach ensures that each user's interactions with the `/api/referrals` endpoint are treated consistently and prevents duplicate state changes.
